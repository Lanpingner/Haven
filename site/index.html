A GPU terminal with the multiplexer already inside it.

Haven is a keyboard-first terminal emulator in Rust. Sessions, window tabs and recursive pane splits are part of the core — not a tmux process layered on top, translating escape sequences twice.

One codebase, one parser, one keymap

The usual stack is a GPU terminal that knows nothing about panes, with tmux inside it re-parsing and re-emitting every byte. That costs a second VT translation layer, a second keymap, a nested-escape-sequence tax, and two programs that disagree about what a cell is. Haven removes the layer by owning both halves.

01 The daemon owns the PTYs

Shells survive client exit, GPU crashes, SSH drops and logout. Several clients can watch one session at once, each with its own size policy and its own scroll position.

02 The GPU does the drawing

Instanced cell quads, a shelf-packed glyph atlas, damage-driven redraws, vsync-paced frames, sRGB-correct colour, and box drawing computed rather than looked up in a font.

03 The core is a pure state machine

haven-core is cells, styles, a grid and VT interpretation — no rendering, no pty, no protocol. You drive it with byte slices, which is why it is testable at all. CI fails the build if it ever links wgpu or winit.

04 The serializer is the parser, inverted

haven-vtwrite turns cells back into escape sequences: damage diffing, SGR coalescing, a per-row cost model, scored scroll detection, synchronized output and OKLab colour downsampling. That is what lets the same client draw into another terminal.

05 Themes are data, not code

The daemon owns the config, so one session looks the same through a window and through SSH, and an edit repaints every attached client without a reattach. Every colour and drawing character comes from the theme; nothing below it hardcodes one.

06 Correctness measured by real programs

mc, vim and less are driven on real ptys in the test suite — including mc under LANG=C, mc's Ctrl+O subshell toggle, and haven tui running inside haven.

It runs three ways from one build

Two frontends over one mux core. Nothing is a degraded fallback: the TUI client is a full client that happens to render with escape sequences instead of triangles.

Server + GPU window

haven gpu attaches a desktop window to the daemon, starting it if needed. Close the window; the session keeps running. Open two; they watch the same panes.

Server + TUI client

haven attach draws the same session into whatever terminal you are already in — over SSH, in a Linux console, inside another emulator. This is the tmux-replacement mode.

Standalone, no daemon

haven tui runs the whole multiplexer in-process with no socket and nothing to leave behind. Plus haven dump and haven screenshot for headless rendering of a program's final screen.

The three levels, named carefully

The word window means two things in a GPU terminal, which tmux never had to deal with. Haven's interface says tab for the thing that owns a pane tree, and keeps tmux's window in the protocol and the commands, with new-tab accepted everywhere new-window is.

desktop windowA haven gpu process. A viewer, not part of a session — several can watch one, and closing one leaves it running.
sessionLives in the daemon and outlives every viewer.
tabOwns a tree of panes, and is named after the command running in its active pane.
paneOne shell, one pty.

How it compares

Haven sits in the Alacritty/kitty class — a native, GPU-accelerated terminal, not an Electron app and not a TUI toolkit — and takes the detachable-server model from tmux rather than expecting you to run tmux inside it. The table below is Haven's own reading of the alternatives; every one of them is a good program, and several are far more finished than this one.

What Haven actually buys you

Over Alacritty / Ghostty

  • Sessions that outlive the window. No tmux needed to keep a build alive when the compositor restarts.
  • Tabs and splits without a second program to configure, bind and keep in sync.
  • The same session over SSH. Attach from your laptop's window, reattach from a console, get the same panes.

Over tmux (inside anything)

  • No double translation. One parser owns the bytes; nothing re-encodes a screen to be re-parsed.
  • One keymap, one config. No disagreement between emulator and mux about what Ctrl+Shift meant.
  • Real key events are the design target (kitty keyboard protocol both directions), not the 1978 control-code collapse.
  • GPU text and scrollback in the same program that owns the panes.

Over kitty

  • Sessions detach. kitty @ controls a live GUI; kill the GUI and the shells go with it.
  • Extensions are specified sandboxed. WASM with declared capabilities rather than in-process Python — once they exist.
  • A TUI frontend for the machine with no display.

Over WezTerm — the closest rival

  • A real terminal frontend. WezTerm's multiplexer is excellent, but attaching to it means running the GUI; Haven's TUI client draws the same session with escape sequences.
  • A much smaller core. ~21k lines of Rust, no Lua runtime, no scripting VM in the hot path.
  • A layering gate in CI that keeps the terminal core unable to link a frontend.

Honestly: WezTerm wins today on polish, platforms, images, ligatures and packaging. Haven's bet is the smaller core and the terminal-side client.

Where Haven loses, today

  • It is v0.0.1. No binaries, no packages — you build it with cargo.
  • Linux/X11 is the tested platform. macOS runs the test suite in CI; the window has not been exercised there. Windows/ConPTY is unwritten.
  • No plugins, no configurable keybindings, no command palette. The prefix table is fixed at Ctrl+A.
  • No italics, no ligatures, no colour emoji in the GPU frontend yet.
  • No sixel, no kitty graphics protocol. Post-1.0 by design, though the cell model reserves image placements so retrofitting them does not touch every file.
  • No tmux wire compatibility. You get tmux's mental model, not its control protocol.
  • Mouse reporting is parsed but not yet encoded back from a client to an application.

Keyboard first, and reachable two ways

Ctrl+A is the prefix. Every key resolves to the same declarative action the command line does, so nothing is reachable one way and not the other.

The command line

Tab completes as far as the candidates agree. A box above the bar lists what matches as you type; ↑ and ↓ walk it and put the highlighted entry on the line, so what Enter runs is always what is written there.

Scrollback

The wheel scrolls whichever pane the pointer is over — not necessarily the focused one. While a pane is scrolled the bar says so, its cursor is not drawn, and typing returns to the live screen. The offset is per client, so two people on one session read at their own pace.

Tab names

A tab is named after the command its active pane is running, which needs the shell's OSC 133;C mark. fish reports it natively; bash and zsh do once Haven's integration is installed, which is automatic unless --no-integrate is passed.

Themes the daemon owns

Because the configuration lives server-side, an edit reaches every attached client — the window on your desk and the client on the other end of an SSH connection — without reattaching. The file is re-read when its timestamp moves. 

# ~/.config/haven/config.toml
theme = "nord"
# haven · nord · gruvbox · daylight
# slate · ansi · plain
# or your own, inline or as
# ~/.config/haven/themes/mine.toml
[theme]
base = "gruvbox"
name = "mine"
bar_session = { fg = "#1d2021", bg = "#83a598", bold = true }
selection   = { fg = 0, bg = 12 }
glyphs      = { here = "*" }

Colours are "#rrggbb", a palette index, or "default" to leave it to the terminal. plain uses no colour and no box drawing, for a terminal that cannot manage either. A broken theme is reported on the daemon's stderr and the interface keeps the default rather than refusing to paint.

Honest status

Usable, with plenty still ahead. mc, vim and htop render correctly; sessions, splits, tabs, zoom, attach/detach, shell integration, themes and a GPU window all work. The design plan tracks exactly what exists, milestone by milestone, so the document cannot drift from the tree.

Working

  • Terminal core — byte-budgeted scrollback, reflow with cursor tracking, alternate screen, scroll regions, insert/delete, erase modes, tab stops, REP, DECSCUSR, DECSTR, DEC Special Graphics, grapheme clusters.
  • Full colour — 16 / 256 / truecolor, both ; and : SGR forms, OSC 4/10/11/12/104/110-112 set and query, OSC 7/52.
  • Mux core — n-ary pane trees with fractional weights, a layout solver with proptest properties, named layouts, zoom-as-override, geometric focus movement.
  • Daemon and attach/detach — framed postcard over a unix socket, per-client row-revision sync, Smallest/Latest resize policies, autostart, protocol-version check at the handshake.
  • GPU frontend — wgpu pipelines, glyph atlas, font fallback, sRGB-correct colour, procedural box drawing, and haven screenshot so the renderer is reviewable with no display.
  • Shells — bash, zsh, fish and generic behind one trait, with correct job control, signals, environment and ZDOTDIR/--rcfile shims.
  • Status bar, command line, completion, session tree, scrollback reading.

Not written yet

  • Plugins. The WASM host and the WIT world are specified in §15 and nothing is built.
  • Copy mode and the modal key table — in progress on master.
  • Configurable bindings and a command palette.
  • The interactive capability probe. Host detection is environment-based guessing today; the probe with timeouts and per-TERM caching is still owed.
  • Live daemon upgrade — a new binary currently needs the daemon restarted.
  • Italic faces, ligatures, colour emoji in the GPU window.
  • Sixel and the kitty graphics protocol — post-1.0.

Notes from the bug log

The plan keeps a record of what each piece of work actually broke, because the interesting failures were never where they looked. Three worth repeating:

A line through every blank cell. CSI > 4 ; 1 m is XTMODKEYS, which fish sends before every prompt. Read as SGR 4;1 it set underline and bold on the pen and nothing ever reset them. A private parameter marker changes what a final byte means; private sequences other than DA2 are now ignored rather than run as their public namesakes.

"Takes forever to render" had nothing to do with the GPU. The fallback font scan set its "already scanned" flag only when it found a face, so a character no font covers rescanned 3829 faces and 8.6 GB every time it appeared. A prompt with three emoji took 5.69 s, of which 5.56 s was syscall time. Mapping the faces once brings it to 0.249 s.

The window-manager freeze was not winit, vsync or the event loop. Measured with a standalone probe: on a hybrid laptop, presenting across PRIME while the WM unmaps the window blocks the X server itself — a bare GetInputFocus on an unrelated connection took 2050 ms. A terminal has no use for a discrete GPU, so the integrated one is now the default.

Architecture

Twelve crates, each with one job, arranged so the terminal core cannot reach a frontend and the frontends cannot reach each other. CI enforces the top of that list.

haven-coreCells, styles, grid, VT interpretation. No rendering, pty or protocol — a pure state machine you drive with byte slices.
haven-ptyPTY allocation, child launch, job control, window sizing.
haven-shellShell detection and per-shell integration behind a Shell trait.
haven-vtwriteCells back to escape sequences: the inverse of the parser.
haven-muxSessions, windows, pane trees, the layout solver, the pane runtime.
haven-protoWire types, framing and transports.
haven-clientFrontend-agnostic client: frame model, input encoding, event loop.
haven-tuiThe TUI frontend: ANSI output, raw mode, input decoding.
haven-renderThe GPU frontend: wgpu pipelines, glyph atlas, procedural box drawing, the window.
haven-daemonThe mux server.
havenComposition root: the CLI and the standalone mux.
winit-probeA standalone winit/wgpu probe, kept because it is what found the X-server stall.

Deliberate deviations

  • The daemon uses a poll loop, not tokio. The pane pump was already poll-based and nothing here benefits from task-per-pane concurrency.
  • The daemon was built before the plugin host, because plugins are specified to run in the daemon — building the host first would have meant building it in the wrong place and then moving it.
  • The status line and tab bar are built-in rather than plugins, but both are already pure functions of state, which is what makes inverting that cheap later.

Build it

Rust 1.85 or newer, and a GPU backend wgpu can reach for the window. There are no packages yet; this is a from-source project for now. 

git clone https://github.com/berromaa/HavenTerminal
cd HavenTerminal

cargo test --workspace            # 400 tests, incl. mc/vim/less driven on real ptys

# A GPU window, attached to the daemon (which it starts if needed).
cargo run --release -p haven -- gpu

# The same session in your current terminal.
cargo run -p haven -- attach
cargo run -p haven -- ls
cargo run -p haven -- server stop

# Standalone: the whole mux, no daemon. Ctrl+A is the prefix.
cargo run -p haven -- tui

# Headless: print or render a program's final screen.
cargo run -p haven -- dump --cols 80 --rows 20 -- mc -u
cargo run -p haven -- screenshot --out mc.ppm -- mc -u
cargo run -p haven -- shell-info

Subcommands: gpu, attach, tui, ls, kill-session, server, dump, screenshot, shell-info. CI runs fmt, clippy with -D warnings, and the full test suite on Linux and macOS, plus a layering gate asserting that haven-core cannot link wgpu or winit.
